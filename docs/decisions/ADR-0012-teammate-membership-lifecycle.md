# ADR 0012: Teammate membership identity and shutdown

Status: Draft (implementation pending coordinator acceptance)

## Decision

A teammate's display name is an alias, not its durable identity. Each roster membership has an immutable `membershipId`; legacy persisted roster entries receive an ID once when loaded and are persisted through the existing roster store. New membership creation allocates a fresh ID. Historical runs and transcripts remain untouched.

Shutdown is a destructive membership operation, distinct from release: it must fence new admissions, cancel queued or active work, verify owned resources are disposed, reconcile task attempts/claims only after settlement, archive mailbox state by membership, and only then remove live membership. Failure to verify cleanup must retain recovery ownership and prevent alias reuse. No worktree or transcript is deleted.

## Migration, compatibility, and recovery

New lifecycle contracts are only `busy | idle | released`; `retired` is accepted only by the persisted-roster decoder as legacy input. Every legacy retired member is normalized to `released + unavailable` with the durable `recoveryFence: legacy-retired-unverified` marker; it is not archived merely because an error/receipt is absent. Startup correlates by exact membership ID first; missing or contradictory teammate names are retained as unresolved rather than treated as unrelated. It archives a legacy identity only when at least one exact-incarnation run receipt is correlated and every such receipt has a handle that is positively disposed. Missing-handle and incompatible registry rows remain persisted and fence the membership; an opaque incompatible row conservatively fences all current memberships. Successfully disposed terminal outcomes retained solely because `rememberAgents=false` carry a validated handle-less `cleanupProof` bound to the run ID and optional membership ID; the parser accepts it only for a terminal row with no handle and a finite nonnegative verification time. That durable proof survives registry sync/restart and is distinct from arbitrary missing-handle rows. Arbitrary missing-handle rows remain unresolved receipts. With no correlated receipt, cleanup cannot be proven and the alias stays fenced for manual resource recovery rather than guessed safe. Ordinary release, fresh admission, and cold resume cannot clear this fence; shutdown may remove it only after exact ownership disposal. Legacy roster IDs are backfilled once and atomically persisted; if a required recovery-fence write fails, startup throws, manager admissions remain blocked, and the admission epoch is incremented so in-flight model/cleanup admissions revalidate before run registration.

Legacy mailbox messages without `toMembershipId` are rejected/quarantined for an incarnation-bound recipient. Legacy run history without `membershipId` remains readable, but named cold resume is denied when a later same-name membership exists; history stays available for inspection. Legacy task ownership is only bound when a settled attempt proves exact membership ownership; ambiguous claims remain fail-closed and require explicit board recovery. Migration does not delete unknown/newer schema files. Older binaries are not safe writers after this migration: integrators should require the first release containing this roster normalization before downgrade/rollback; backup the team directory before rollback, and do not map legacy retire to destructive shutdown. The current development SDK floor is Pi 1.0.4 (dev dependency range `>=1.0.4 <1.1.0`; peer dependencies remain `*`); a loader-registration check on installed 1.0.4 is not proof for the entire declared range. Release notes should name the first migration-capable plugin version as the downgrade floor.

## Lock/call inventory (source audit)

| Entry/call path | Lock / mutation | Ordering and evidence |
| --- | --- | --- |
| Admission, release, mailbox assignment; `AgentManager.allocate`, `release`, `adoptMailboxAssignment` | Per-name promise gate (`withTeammateLock`, `app/agent-manager.ts`); synchronous roster/mailbox operations may then take mailbox mutation lock | Teammate → mailbox; never await another teammate operation while holding mailbox lock. |
| Shutdown; `shutdownTeammateCore` | Persist intent and task fence before asynchronous cancellation; wait for stop/finalize without teammate lock; acquire teammate lock only for verified final disposal/removal | No teammate lock during stop/finalizer awaits; all correlated stale receipts are verified before `resources_disposed`; unresolved no-handle/incompatible rows prevent phase advancement/removal; handle-less verified history is excluded from receipt scans. |
| Mail send/receive/archive; `MailboxService.send`, `discardPending` | `withMailboxMutationLock` (`app/mailbox-lock.ts`) | Mailbox lock is not held while awaiting task or process work. Contention fails closed/retry. |
| Task reconciliation; `TaskExecutionService.reconcileTeammateShutdown` | Task-board service mutation boundary | Called outside the teammate gate during shutdown fence/reconcile; it does not acquire a teammate gate. |
| Roster `setShutdownOperation`/`removeMember`/legacy fence migration | Mailbox mutation lock | Only synchronous roster mutation/persist; `removeMember` rejects recovery fences unless shutdown passes verified cleanup proof. |

Public UI projection is `AgentManager.teammateStatus` → `app/ui-snapshot.ts` → `domain/ui-view.ts`; released and busy are projected, archived identities are not roster rows. Autocomplete/message routing uses `pi/teammate-routing.ts` and fails closed on missing/unavailable status. History rows come from the run registry and retain outcome independently of membership; `AgentManager.resume` and all allocation plan kinds reject a recovery-fenced membership.

Native process ownership, force-kill behavior, restart recovery with unresolved child receipts, and actual TUI progress have not been verified; automated fakes are not platform evidence. Installed SDK minimum 1.0.4 loader coverage is reported separately; it does not prove the complete supported version range or native busy-steer.
