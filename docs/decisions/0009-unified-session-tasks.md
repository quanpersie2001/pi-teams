# ADR 0009: Unified session-scoped Tasks

- **Status:** Accepted
- **Supersedes:** the task-domain separation and namespaced shared-board decisions in [ADR 0005](./0005-separate-task-and-agent-domains.md) and [ADR 0007 §4](./0007-session-bound-agent-teams.md), while preserving their historical record.

## Decision

Merge the `references/pi-tasks` task workflow into pi-teams as one unified, session-scoped task board. `Task` and `AgentRun` remain distinct entities: a task contains work requirements and outcomes; attempts refer to AgentManager runs and do not turn a run into a task. Tasks are persisted only for the active session/team. Task writes atomically use schema version 2 with `requirementRevision`, `spec`, `context` and `attempts` present. Reads accept v2 only when those fields and task/attempt/snapshot structures validate. Unversioned legacy and explicit v1 records normalize missing revision to 1 and missing spec/context/attempts to empty values while preserving supplied valid fields; their next write upgrades to v2. Other or malformed schema versions are rejected, not downgraded.

The public task tools are `tasks_create`, `tasks_list`, `tasks_get`, `tasks_update`, `tasks_cancel`, `tasks_execute`, `tasks_output`, and `tasks_stop`. Tasks carry typed `spec`, `context`, `outcome`, requirement revisions/snapshots, dependency/blocker information and attempt history.

Claiming is explicit (`pending` to `in_progress`). Execution settles an attempt, not the task. Completion is a separate explicit owner/coordinator acceptance, optionally preceded by requested review (`in_review`). Stopping an execution marks its attempt stopped and never completes or cancels the task. Cancellation is a separate operation restricted to eligible pending tasks.

Optional task automation is configured through nested settings `tasks: { autoCascade: false, reminders: false }`, with both features off by default. A per-task root `executionPlan` (`type`, optional `name`, `color`, `model`, `maxTurns`) is supplied at create/update, not at `tasks_execute`, and is frozen into execution requirements. On a pending task, `tasks_update { executionPlan: null }` removes the plan and increments the requirement revision; an empty `expectedOutput` is an explicit spec patch. When enabled, cascade snapshots statuses at startup (no replay of existing completions) and observes new accepted transitions to `completed` through local board events and the shared filesystem watcher, including newly discovered completed rows and peer board-service completions. IDs/codes are coalesced and dispatch is deferred to a microtask; pending planned dependents run only if a dependency matches a completed ID/code and all blockers are clear. UI and automation filesystem watchers are ref-counted and dispose independently. Cascade uses normal TaskExecutionService/AgentManager admission and launches each planned task at most once per service. It passes the observed `expectedRequirementRevision` and `expectedStatus: "pending"` to reservation, which validates both atomically before mutation and prevents a stale pending decision from overwriting a concurrent manual claim. A precondition mismatch (including a concurrent plan change/clear such as `type`, `name`, or `model` while waiting to reserve) skips the automatic launch before spawn without owner/attempt mutation and clears its deduplication entry without immediate rescheduling. The pending-status guard is automation-only; manual `tasks_execute` can execute unblocked pending or claimed tasks (non-coordinators must own a claimed task). Typed reservation-lock conflicts receive bounded asynchronous retries (100/250/500 ms) before launch, but spawn failures do not; retry exhaustion clears deduplication for a later completion trigger. Cancellation/disposal suppresses retries and queued work, and post-reservation cancellation rolls back before spawn. Session teardown disables reminders/disposes automation and freezes admissions before child shutdown. Lead-only reminders run every four lead turns, reset on `tasks_*` tool results, and append a hidden transient context message with relevant lead-owned/assigned pending, lead-owned in-progress, or review-requested in-review tasks. They are bounded to 10 items/1,700 serialized JSON characters and omitted when no tasks are relevant; children receive no reminder.

The public events RPC remains a compatibility surface for third-party consumers; the default RPC owner may remain `pi-tasks`. This does not make RPC the built-in task workflow or imply that compatibility was removed. Disable the separate legacy `pi-tasks` extension when using unified Tasks; its standalone workflow is not supported as the unified board. Interactive manual TUI smoke testing remains pending. The unified task implementation uses no copied external content.

## Consequences

- Unified Tasks tools are the first-party task workflow; external integrations may continue using the retained RPC contract.
- Task scope is session-bound, not durable across sessions as a managed workflow.
- The historical separation described by ADRs 0005 and 0007 is superseded, not rewritten.
