# ADR: isolated local peer messaging

Status: authenticated Unix-domain transport and Pi host wiring implemented. The local native-SDK smoke exercises two independent `AgentSession`s, signed delivery, API approval, and SDK acceptance; production host-loader registration and interactive TUI approval remain unverified. Windows named-pipe transport remains fail-closed behind a required host ACL-verification callback.

Use a per-runtime Unix-domain socket for local ingress plus an owner-only filesystem registry/inbox/receipt store. No daemon, Herdr, tmux, or shared team secret. Discovery uses canonical `projectId` (Git common-dir for worktrees, explicit canonical root for non-Git). Runtime addresses include stable session ID and fresh runtime incarnation; old-runtime mail is never read by a new incarnation.

Sender identity uses Ed25519. Each runtime advertises its SPKI public key; ingress resolves the exact fresh sender session+runtime to that key and verifies a signed versioned message/timestamp/nonce frame before atomic acceptance. Acceptance binds an immutable full-envelope fingerprint, applies durable per-sender rate limits and aggregate quota, and atomically enqueues. It rejects unknown/stale sender keys, wrong recipient runtime, expired or >1-hour TTL frames, timestamps >60 seconds in the future, replayed nonces, malformed/oversized frames, and conflicting duplicate IDs. `PeerMessagingService.receive(envelope)` checks the durable immutable binding; callers cannot assert sender identity. Refused, expired, and delivered receipts are terminal tombstones. A `queued` response means verified durable enqueue, not model delivery.

On Unix, the socket parent must be current-user-owned/private and socket mode is 0600; the storage adapter rejects symlink traversal (allowing macOS /var and /tmp canonical aliases) and requires owner-only directory modes. On Windows, a named pipe is implemented, but both ingress and `LocalPeerHost` fail closed unless the host supplies a verifier returning true for the per-user storage ACL. The callback is a security-critical host responsibility; this repository does not implement or prove Windows ACL inspection. Same-user malicious processes that can read runtime private keys or modify the private data root are outside the isolation guarantee. Private keys must never be placed in shared project storage.

Inbound policy is receiver-owned and defaults to `hold`; project settings cannot elevate it. Peer text is untrusted plain text and does not grant lifecycle/task authority or share transcript/thinking. Bounds: 16 KiB UTF-8 body, 100 pending+held messages per runtime, and 10 inbound messages per sender runtime per 10 seconds. Inbox/held transfer and ingress quota checks share an atomic filesystem lock. In-flight receive/approval uses per-message exclusive claims (5-minute stale lease; a live owner PID prevents lease stealing). Receipt states are append-only markers with terminal precedence, so queued cannot regress terminal state. Bindings/tombstones persist for seven days after envelope expiry; records are capped at 10,000 bindings and 10,000 rate identities; at most 10,000 distinct receipt IDs can be introduced between cleanup runs, with up to three transition markers per ID (30,000 marker files). Cleanup occurs on ingress (at most once per minute) and is also exposed as `LocalPeerHost.prune`; hosts should invoke prune periodically. Delivery remains at-least-once; no claim of exactly-once side effects.

Peer delivery through the wired runtime dispatches `sendUserMessage` with a unique correlation marker and only treats the matching SDK `message_start` event as acceptance. A bounded missing-ack timeout is ambiguous: pending mail is preserved, and retry may duplicate delivery. The offline native smoke exercises two independent SDK sessions through signed runtimes and hold/approval/acceptance; it uses a thin adapter and does not verify production loader registration, interactive TUI approval, or busy SDK steering.

## Integration recipe

1. Resolve scope with `resolvePeerProjectId(cwd, explicitNonGitRoot?)`. Provision a current-user-owned mode-0700 data directory; do not put private keys or sockets in a shared/project directory.
2. For each **main session only**, generate an Ed25519 keypair and a fresh `runtimeId`; get endpoint path from `createPeerEndpointPath(privateRoot)`. Start `startPeerIngress({ address, socketPath, resolveSenderKey: createPeerKeyResolver(host, projectId), mailbox: host, verifyWindowsStorage })` (Windows verifier mandatory). Only after ingress successfully starts, publish a `PeerAdvertisement` with `identityPublicKey` as SPKI PEM and endpoint kind `unix` or `named_pipe` matching the platform; publish heartbeat/status. Keep private key in runtime memory or verified owner-only storage.
3. Instantiate `PeerMessagingService` with `createPeerTransportSender(privateKey, resolveEndpoint)`; resolve endpoint by exact recipient session+runtime from validated registry ads. `PeerMessagingService.send` fails closed without this authenticated transport. For accepted inbox items, call `PeerMessagingService.receive(message)`; it checks the durable fingerprint/sender binding and acquires the per-message claim. Poll `LocalPeerHost.pending(localAddress)` and retain delivery failures for retry; call `host.prune()` periodically. This package does not supply a scheduler.
4. On session shutdown, stop polling, close `PeerIngress` (which removes its socket), and unregister the exact advertisement. Never reuse runtime ID, key, or endpoint on restart. Do not automatically resume closed sessions.
5. Instantiate messaging with receiver-owned immutable policy defaulting to `hold`. Surface `heldMessages()` and explicit `approveHeld(id)` / `refuseHeld(id)` actions; no held body reaches the model before approval. Use the serialized `SafePeerSdkAdapter` hook for validated idle/busy delivery.
6. Register `createPeerTools(...)` handlers as `peer_sessions`, `peer_send`, `peer_activity`; do not expose lifecycle operations. Exported APIs: `startPeerIngress`, `PeerIngress.close`, `sendPeerMessage`, `createPeerTransportSender`, `createPeerKeyResolver`, `PeerDiscoveryService`, `PeerMessagingService`, `LocalPeerHost`, `SafePeerSdkAdapter`, `resolvePeerProjectId`, `createPeerTools`; contracts `PeerAddress`, `PeerAdvertisement`, `PeerPolicy`, `PeerMessage`, `PeerReceipt`.

## Verification limits

Unix-domain ingress was exercised with a separately spawned Node child process, not a commercial provider or Pi host. Authentication/send/receipt, wrong-key spoof, nonce replay, refused-ID replay/conflicting body, TTL/future timestamp, per-sender burst, stale sender/recipient and closed-target cases are covered by `test/integration/peer-transport.test.ts`; concurrent quota, immutable binding, retention, receipt monotonicity, and claims are covered by `test/unit/peer-host.test.ts` and `test/unit/peer-messaging.test.ts`. A Windows-conditional child-process named-pipe test is present but was not run here; it uses a test verifier stub and does not prove Windows ACLs. Production host-loader registration and interactive TUI approval, plus a real Windows ACL verifier, remain integration/platform verification work. `peer-sdk-native-smoke.test.ts` exercises two independent local SDK sessions and the approval API using an offline test provider.
